# 經驗紀錄

## 2026-11-23：圖片生成完成，不代表網站收到正確圖片

### 現象

GitHub Actions 顯示成功，但故事封面仍和標題不符，文章內也沒有預期的三張插圖。

### 根因

- 生成流程原本只產生封面和一張場景圖。
- 生成器傳送的是完整圖片網址；網站 `upsert_story()` 把所有 HTTP(S) 圖片都當成外部圖片，改指派本機隨機圖，因此標題導向的生成圖被丟棄。
- 桌機頁面的文章內插圖依賴影片 manifest。停用影片流程後，新故事沒有 manifest，原本的插入程式就不會顯示場景圖。
- 圖片生成錯誤原本會被記錄後繼續存故事，所以工作流程成功不保證圖片數量完整。

### 經驗與處理方式

圖片需求要從生成、上傳、同步、資料庫儲存到桌機與手機顯示逐段確認，不能只看 Actions 綠勾或生成器日誌。

- 每篇故事固定需要一張封面和三張場景圖；四張共用風格與色盤骰子，場景各自抽構圖、光線和細節。封面以標題為主要視覺依據，避免額外的隨機元素蓋過題目。
- 必要圖片未全部生成並上傳時，不發布該篇故事，避免成功狀態掩蓋缺圖。
- 網站只接受同站 `/images/` 下存在的 WebP 檔，存回檔名而非完整網址；拒絕任意外部主機與路徑。
- 故事頁直接讀取三張場景圖，分布到文章段落；不再依賴影片 manifest。缺圖時不以隨機圖片冒充故事插圖。
- 讀取既有故事時，若找到同 story code 的生成圖片檔，優先恢復正確封面與場景圖。

### 下次排查順序

1. 確認 Action 產生了哪些檔案，以及每張圖是否上傳成功。
2. 確認通知 API 收到的 `cover_image` 與三張 `scene_images`，以及資料庫最後儲存值。
3. 確認桌機和手機頁取得這些檔名並載入圖片；查清是否有舊版隨機圖或 manifest 邏輯覆蓋新流程。
4. 對照「每篇一封面、三插圖」驗收，不以 workflow exit code 單獨判定完成。
