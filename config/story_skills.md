# ODDITY HUB 故事生成 Skills

這份文件是供 scripts/main.py 在 GitHub Actions 執行時直接讀取的寫作規範。它整合參考專案的工作流程概念與本專案需求，不直接複製第三方專案內容，也不依賴 Claude Code 專用指令。

## 寫作執行流程

每次生成都依序完成以下階段；階段內容只用於生成與修訂，不輸出分析過程、草稿或檢查清單。不要跳過提綱直接擴寫素材，也不要在最後修訂時添加未鋪墊的新事實。

### 階段 1 — 素材判讀
- 判斷素材屬於近期新聞或歷史案件，區分可核對資訊、來源說法、推測、爭議與未知。
- 近期新聞只取抽象異常概念；歷史案件只取可安全轉化的調查結構、線索模式或未解問題。
- 列出不得帶入故事的真實識別資訊；來源摘要不足時，不補造案件事實。

### 階段 2 — 情節提綱
- 先確定主角目標、阻礙、異常規則、至少兩個線索、合理誤導、轉折及結局回應。
- 把骰選的視角、敘事結構、節奏、揭露密度與結局安排到情節順序中，而非只在 metadata 留下標籤。
- 檢查提綱能否形成因果鏈；若結局依賴尚未出現的線索，先調整提綱。

### 階段 3 — 正文初稿
- 按提綱寫出繁體中文故事，維持人物知情範圍、動機、時間線和異常規則。
- 每個場景至少推進情節、揭露人物或改變讀者理解之一；不為湊字數重複解說。
- 以人物選擇、具體動作與可感知細節呈現恐懼，避免新聞報告腔和抽象情緒判詞。

### 階段 4 — 連貫性與語句修訂
- 對照提綱檢查線索先後、誤導公平性、轉折因果、人物動機、資訊取得與結局回應。
- 先修正矛盾或缺失，再刪除重複、空泛形容和制式句；不改變已成立的故事事實。
- 檢查骰選設定確實體現在正文中，且不把未證實來源內容寫成真實案件事實。

### 階段 5 — HTML 與 JSON 定稿
- 將完成的正文排成安全 HTML 片段，遵守下方閱讀排版與標籤限制；格式化不得改寫劇情。
- 檢查 JSON 欄位、繁體中文、字數與標籤閉合後，只輸出既定 JSON，不附帶階段說明。

## Skill 1 — 案件來源分析
- 區分來源中可直接核對的資訊、來源作者的說法、推測、爭議及未知事項。
- 保留原始來源 URL；不能因為出現在搜尋摘要就宣稱已獨立查證。
- 抽取可轉化為虛構創作的結構：調查順序、線索出現方式、時間線矛盾、證詞差異、環境條件與未解問題。
- 不把真實人物姓名、可識別細節或真實受害者的痛苦當作獵奇裝飾。
- 歷史案件資料不足時，承認不足，不得自行補造「案件事實」。

## Skill 2 — 故事架構設計
在撰寫正文前，先於內部規劃：
1. 主角的具體目標與阻礙。
2. 核心異常／謎團，以及故事世界內可理解的規則。
3. 至少兩個會在後續產生作用的線索。
4. 至少一個合理但錯誤的解釋或誤導。
5. 轉折如何改變讀者對先前事件的理解。
6. 結局如何回應主要問題，或有意識地保留哪一個問題。
骰子指定的結構、視角、節奏、揭露密度及結局都必須真正反映在故事中，不能只在 JSON metadata 裡填值。

## Skill 3 — 懸疑與連貫性檢查
交付前逐項自查：
- 時間、地點、人物移動及資訊取得順序是否互相矛盾。
- 每個重要行動是否有動機；角色不能無故知道尚未揭露的資訊。
- 線索是否先於答案出現，解答是否依賴讀者從未得到的資訊。
- 誤導是否公平，轉折是否能重新解釋前文而不是推翻所有規則。
- 超自然／科幻規則是否前後一致。
- 結局是否回應主線；開放結局仍須讓核心衝突有所推進。
發現問題時，先修正故事，再做語句潤飾。

## Skill 4 — 繁體中文「活人感」修訂
- 避免新聞報告腔、制式的「突然感到一陣恐懼」、空泛形容詞堆疊及反覆解釋同一情緒。
- 用角色選擇、動作、物件、聲音、氣味、光線和具體後果呈現恐懼。
- 每個場景至少推進情節、揭露人物、改變讀者理解三者之一。
- 句長需有變化；緊張場面可以短句，但不要整篇都像預告片台詞。
- 對白應呈現角色差異，避免所有人都用相同語氣解釋背景。
- 刪除沒有提供新資訊、情緒或節奏作用的重複句。

## Skill 5 — HTML 閱讀排版
- 故事標題由獨立 title 欄位顯示；正文不重複完整標題。
- 長篇依情節分成約 3–6 個章節，章節提示使用網站現有安全標籤可保留的粗體段落：<p><strong>第一章｜章節名稱</strong></p>。
- 一般段落約 2–5 句；不要整篇塞在一個段落，也不要每句都硬拆段。
- 每位角色的重要對白應清楚分段；內心活動可用 <em>，關鍵線索可少量用 <mark>，重要瞬間可少量用 <strong>。
- 場景切換可用獨立的斜體短段落，不使用可能被網站清理的標籤。
- 僅使用網站提示允許的 HTML 標籤；所有標籤正確閉合。排版不得改寫劇情或添加新事實。

## 輸出要求
最終只輸出指定 JSON 結構。以上分析、規劃和檢查留在內部，不要把檢查清單或推理過程放進故事正文。

## 參考專案與採用方式
- Sumeru — https://github.com/xindoo/sumeru ：採用「先規劃、再寫作、再檢查」的分階段工作流程概念；不搬入長篇小說專用功能。
- Oh Story — https://github.com/zenstory-ai/oh-story-claudecode ：參考中文故事寫作與潤飾流程；不依賴 Claude Code 專用命令。
- story-skills — https://github.com/bs779517/story-skills ：作為故事素材與寫作流程模組化的參考；不假設其工具可直接在 GitHub Actions 執行。
- Human Writing — https://github.com/KKKKhazix/human-writing ：參考降低報告腔、避免重複、強化場景作用及修訂檢查的方向。
